# 多上下文控制模型重构（实施计划）

## 一、背景与目标

### 为什么要改

现有控制权模型是「**单占用者 + FIFO 排队 + 输出广播给所有订阅者**」：一台 bot 上只有一个 shell 进程，所有人看同一条输出流，同一时刻只有一个人能输入，其余排队。实现集中在 `helper/internal/core/{bot,occupancy,idle}.go`、`helper/internal/webui/server.go` 的 `handleTerm`，以及 `user/internal/term/shell.go` 的单 `ShellManager`。

实际使用中这套模型的核心价值（实时围观他人操作）被判定为无用，真正需要的是**多人各自独立地操作同一台机器**。因此整体替换为：

> 每个普通用户在一台 bot 上拥有**各自独立的操作上下文**（被控端一个独立 shell 进程），默认可同时操作、互不干扰、互不可见；跨用户观看或接续操作需**发起授权申请**；观看方的输出按「被观看者完成一次操作」的粒度同步，而非实时。

### 目标

1. 被控端从「一个 shell」改为「**每上下文一个独立 shell 进程**」，cwd / 环境 / 交互式程序状态互相隔离。
2. 上下文**默认私密**，跨用户访问走申请—授权流程，授权**直到主动撤销**止。
3. 观看方按「**一条命令跑完**」为一段接收输出，所有者本人仍是实时。
4. 上下文 **1:1 绑定 (用户, bot)**，且**跨连接可恢复**（恢复 cwd 与命令历史）。
5. 底部面板（dock）绑定「**当前操作上下文**」。
6. 新增持久化概念：**用户ID → botID → 操作上下文**。

### 本次范围

**只做控制模型重构。** 文件传输（上传 / 下载 / SHA-256）依赖「当前上下文」的归属模型，待本次落地后另立计划。

## 二、核心概念与规则

| 概念 | 定义 |
|---|---|
| **操作上下文（Ctx）** | 一个用户在一台 bot 上的一条独立操作线，对应被控端一个独立 shell 进程 |
| **上下文 ID** | `ctxID`，由 helper 侧生成（形如 `c_<botID>_<ownerID>`），全局唯一，贯穿协议与 DB |
| **所有者（owner）** | 该上下文的创建者，对它有完整权限，可授权他人、可收回 |
| **观看（watch）** | 只读，按「段」接收输出 |
| **接续（operate）** | 可输入；同一上下文同一时刻**只有一个输入持有者** |
| **段（segment）** | 从一次提示符出现到下一次提示符出现之间的输出，即「一条命令跑完」 |

### 规则

1. **创建**：普通用户（角色 ≥ 2）打开某 bot 的终端时，若该 (user, bot) 尚无上下文则自动创建。每 bot 上下文数上限 `maxContextsPerBot = 5`，超出拒绝并提示。
2. **隔离**：不同上下文各自独立 shell，互不可见、互不影响（`cd` 不串）。
3. **私密**：默认只有 owner 能看到自己的上下文。观察者（角色 1）不创建上下文，只能作为观看者存在。
4. **申请与授权**：他人可对某上下文发起 `watch` 或 `operate` 申请；owner 同意后建立授权记录，**长期有效直到主动撤销**。
5. **用户级「默认可看」**：用户在设置里开一个总开关，开启后**所有属于他的上下文默认对所有人开放只读**（仍不可输入）；单个上下文可在授权列表里单独关掉。
6. **同步粒度**：owner 实时；watcher 只在收到段结束标记后拿到该段输出。watcher 接入时先回放最近 64KB 已完成的段。
7. **接续**：同意 `operate` 申请时，输入锁**立即移交**给申请者，原持有者变为只读并收到「已被接续」提示；owner 可随时「收回」，收回 = 删除该授权 + 输入锁回到 owner。
8. **恢复**：上下文持久化在 DB。重连时若被控端该 shell 仍存活则直接复用；若 shell 已消失（bot 重启 / helper 重启），则新建 shell，把 DB 里记录的 `cwd` 用 `CtxOpen.Cwd` 带下去执行一次 `cd`，并把该上下文最近的**段回放**播种回终端（见 §六.4），实现「画面持久化回放」，跨重启不丢。

## 三、协议改动

两端 `protocol/message.go` **必须同步修改**（`helper/protocol` 与 `user/protocol` 是两份独立副本）。

### `Message` 新增字段

```go
CtxID string `json:"ctxID,omitempty"` // 操作上下文 ID（终端类消息必备）
Seq   int    `json:"seq,omitempty"`   // 段序号：段结束标记用；ctx_open 时表示新 shell 的起始段序号（续接历史，跨重启不回绕）
Mode  string `json:"mode,omitempty"`  // 授权模式：watch | operate
Err   string `json:"err,omitempty"`   // 上下文打开失败等错误
```

### 新增消息类型

| 常量 | 方向 | 作用 |
|---|---|---|
| `TypeCtxOpen` | helper→user | 请求开启/复用一条上下文（`CtxID`、`Cols`、`Rows`） |
| `TypeCtxOpened` | user→helper | 上下文就绪（`CtxID`、`Err` 非空表示失败） |
| `TypeCtxClosed` | user→helper | 该上下文的 shell 已终止 |
| `TypeCtxSegEnd` | user→helper | 一段操作结束（`CtxID`、`Seq`）；helper 据此封段并推给 watcher |

### 改动既有类型

- `TypeInput` / `TypeResize`：**保留名称**，新增必填 `CtxID`；被控端按 `CtxID` 分发到对应 shell，缺失或未知 `CtxID` 直接丢弃。
- `TypeOutput`：新增 `CtxID`。这是从「无标识广播」变为「按上下文路由」的关键。
- `TypeExec` / `TypeExecResult`：**不动**，一次性命令通道与上下文无关。

> 授权本身不进协议——它是 helper 侧的权限数据，被控端不参与；接续只是改变「谁在往哪个 shell 写」。

## 四、被控端（user）改造

### 1. `term.ShellManager` → `term.SessionManager`（新文件 `user/internal/term/session.go`）

把 [shell.go](file:///d:/AAAGitProject/Remote_control/user/internal/term/shell.go#L36-L44) 的单实例 `ShellManager` 换成按 ctxID 索引的多会话管理器：

```go
type session struct {
    id    string
    shell Shell
    cols  int
    rows  int
    seq   int    // 段序号
    buf   []byte // 段内累积（用于剥哨兵与判定段边界）
}

type SessionManager struct {
    c    Sender
    mu   sync.Mutex
    ses  map[string]*session
    last time.Time // 每个会话各自记录，用于静默兜底
}
```

- `Open(ctxID, cols, rows)`：已存在则复用并回 `TypeCtxOpened`；不存在则 `startShell()` 新建（复用现有 [shell_windows.go](file:///d:/AAAGitProject/Remote_control/user/internal/term/shell_windows.go) 的 ConPTY 启动与 [pty_unix.go](file:///d:/AAAGitProject/Remote_control/user/internal/term/pty_unix.go) 的 pty 启动路径，原样复制即可）。超过 `maxContextsPerBot` 回错误。
- `Write(ctxID, p)` / `Resize(ctxID, cols, rows)` / `Close(ctxID)`：按 ID 路由。
- **保活**：连接断开**不销毁**会话，保留 `sessionIdleTTL = 10min` 后回收；由后台 GC 扫描销毁。bot 进程退出则全部丢失（靠 DB 的 cwd 重建）。
- `Pump(ctxID)`：每会话一个协程，读 shell 输出 → 经哨兵解析 → 发 `TypeOutput{CtxID}`；命中哨兵时发 `TypeCtxSegEnd{CtxID, Seq}`。

### 2. 提示符哨兵（新文件 `user/internal/term/sentinel.go`）

这是「一条命令跑完为一段」的**唯一可行实现**——裸 PTY 没有「命令结束」事件。

- **哨兵格式**：OSC 序列，终端不显示，且**顺带携带 cwd**便于恢复：
  `ESC ] 1337;RA;<nonce>:<cwd> ESC \`（实现见 [sentinel.go](file:///d:/AAAGitProject/Remote_control/user/internal/term/sentinel.go)，cwd 直接以明文拼接，不再 base64）
- **注入方式**：
  - Windows：启动 `cmd.exe /K chcp 65001>nul` 时设环境变量 `PROMPT`，用 cmd 的 `$E`（ESC）构造：
    `PROMPT=$P$G$E]1337;RA;<nonce>:<cwd>$E\`——保留 `$P$G` 原有外观，只在末尾追加不可见哨兵。
  - Linux：启动 shell 前在子进程环境里设 `PS1`（保留用户默认外观 + 哨兵），必要时用 `--rcfile` 注入。
  - 具体两种注入的可行性需在实现时各做一次最小验证（cmd 的 `$E` 与 bash `-i` 继承 `PS1` 的行为）。
- **解析与剥离**：`Pump` 里做流式状态机，识别并**剥离**哨兵字节（所有者与观看者都不应看到它），命中即 `seq++` 并发 `TypeCtxSegEnd`。
- **兜底**：
  1. 输出静默超过 `segSilenceFallback = 800ms` 且无哨兵 → 同样发一个 `TypeCtxSegEnd`（解决 `vim` / `top` 这类永不返回提示符的全屏程序）。
  2. 用户自己改了 prompt 导致哨兵消失 → **保守触发**：连续 `promptReinjectAfter = 5` 段都未命中哨兵才重新注入一次 `PROMPT`/`PS1`。代价是回显一行文本、极小概率干扰全屏程序，因此只在确认哨兵长期失联后才动手。

### 3. `core.Client` 改造（[conn.go](file:///d:/AAAGitProject/Remote_control/user/internal/core/conn.go#L16-L22)）

- `Shell *term.ShellManager` → `Sessions *term.SessionManager`。
- `ReadLoop` 的分发改为按 `CtxID` 路由到对应会话；`TypeCtxOpen` / `TypeCtxClose` / `TypeInput` / `TypeResize` 各加一个 case。

## 五、协助者端（helper）改造

### 1. `core`：新增上下文层（新文件 `helper/internal/core/context.go`）

`BOT` 结构（[bot.go](file:///d:/AAAGitProject/Remote_control/helper/internal/core/bot.go#L57-L94)）删除 `holder` / `queue` / idle 相关字段，改为：

```go
type CtxState struct {
    ID        string
    OwnerID   int64
    OwnerName string
    Sever     map[string]*subEntry // 订阅者：key = 用户ID 或 local
    curSeg    []byte               // 当前段的累积输出
    segs      [][]byte             // 已完成的段（总量上限 64KB，超了从头裁剪）
    seq       int
    inputUID  int64                // 当前输入持有者
}
```

- **输出路由**：bot 来的 `TypeOutput{CtxID}` → 追加到 `curSeg`，**只推给该 ctx 的 owner**；收到 `TypeCtxSegEnd{CtxID}` → `curSeg` 封为一段存入 `segs` 并裁剪，**推给所有 watcher**。
- **订阅**：`SubscribeCtx(ctxID, Subscriber)` 取代 `SubscribeAs`。`Subscriber` 复用 [occupancy.go](file:///d:/AAAGitProject/Remote_control/helper/internal/core/occupancy.go#L40-L46) 的结构，`ReadOnly` 语义改为「是 watcher 还是 owner」。
- **输入锁**：`TakeInput(ctxID, uid)` / `ReleaseInput(ctxID, uid)`；只有 `inputUID == uid` 的输入才转发给 bot。接续时移交并广播 `CtrlRevoked` 给原持有者。
- **保留**：每 ctx 的回放缓冲（原 `outHistoryLimit = 64*1024` 语义不变，只是从「按 bot」变成「按 ctx」）。
- **不引入 DB 依赖**：授权判定放 webui 层（查 DB 后把「owner / watcher / operate」结论传给 core），core 只负责路由与输入锁，保持现有分层。

### 2. `webui/server.go`

- **`handleTerm` 重写**（[server.go](file:///d:/AAAGitProject/Remote_control/helper/internal/webui/server.go#L361-L447)）：路径改 `/api/term?bot=xxx&ctx=yyy`。订阅前先鉴权：owner？有授权？观察者？据此决定是 owner 通道还是 watcher 通道；输入处理改为校验输入锁而非「是否 operator」。
- **根路径 `/`** 与 webui 其余端点保持不变。

### 3. 新增上下文 API（新文件 `helper/internal/webui/context_api.go`）

| 方法 + 路径 | 作用 |

## 六、数据库改动

### 建表方式

[schema.sql](file:///d:/AAAGitProject/Remote_control/helper/internal/store/schema.sql) 是 **`go:embed` + 每次启动全量幂等执行**（[store.go](file:///d:/AAAGitProject/Remote_control/helper/internal/store/store.go#L104-L119) `migrate()` 直接 `db.Exec(schemaSQL)`，只在 `meta` 里缺 `schema_version` 时写入）。因此**新增表只需往 schema.sql 里追加 `CREATE TABLE IF NOT EXISTS`**，老库自动升级，无需版本分支。`schemaVersion` 常量当前为 **3**（v2 引入上下文四表，v3 引入段回放与保留策略）。

### 新增表

```sql
-- 操作上下文：1:1 绑定 (bot, owner)
CREATE TABLE IF NOT EXISTS contexts (
    id             TEXT PRIMARY KEY,
    bot_id         TEXT    NOT NULL,
    owner_id       INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title          TEXT    NOT NULL DEFAULT '',
    cwd            TEXT    NOT NULL DEFAULT '',
    created_at     INTEGER NOT NULL,
    updated_at     INTEGER NOT NULL,
    last_active_at INTEGER NOT NULL DEFAULT 0,
    UNIQUE(bot_id, owner_id)
);

-- 已生效的观看/接续授权（长期有效，直到撤销）
CREATE TABLE IF NOT EXISTS context_grants (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    context_id  TEXT    NOT NULL REFERENCES contexts(id) ON DELETE CASCADE,
    grantee_id  INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    mode        TEXT    NOT NULL,            -- watch | operate
    granted_at  INTEGER NOT NULL,
    UNIQUE(context_id, grantee_id)
);

-- 申请记录（同意后转成 grant，保留申请历史）
CREATE TABLE IF NOT EXISTS context_requests (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    context_id   TEXT    NOT NULL REFERENCES contexts(id) ON DELETE CASCADE,
    requester_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    mode         TEXT    NOT NULL,
    state        TEXT    NOT NULL DEFAULT 'pending', -- pending | accepted | rejected
    created_at   INTEGER NOT NULL,
    answered_at  INTEGER NOT NULL DEFAULT 0
);

-- 用户级偏好（含「默认可看」）
CREATE TABLE IF NOT EXISTS user_prefs (
    user_id       INTEGER PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    watch_default INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX IF NOT EXISTS idx_contexts_owner      ON contexts(owner_id);
CREATE INDEX IF NOT EXISTS idx_contexts_bot        ON contexts(bot_id);
CREATE INDEX IF NOT EXISTS idx_grants_grantee      ON context_grants(grantee_id);
CREATE INDEX IF NOT EXISTS idx_requests_context    ON context_requests(context_id);
```

> 「默认可看」用独立的 `user_prefs` 表而非给 `users` 加列——SQLite 没有 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`，独立幂等建表最干净。

### 4. 命令历史回放与保留策略（v3 起）

早期只存「段序号 + cwd」的 `context_commands` 表**只写不读**，无法真正回放画面，v3 起替换为下面两张表（`schemaVersion` → 3，并在 `migrate()` 里 `DROP TABLE IF EXISTS context_commands` 清掉旧表）。

```sql
-- 段回放：每条上下文按段持久化原始输出，用于重连后恢复画面
CREATE TABLE IF NOT EXISTS context_segments (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    context_id TEXT    NOT NULL REFERENCES contexts(id) ON DELETE CASCADE,
    seq        INTEGER NOT NULL,
    cwd        TEXT    NOT NULL DEFAULT '',
    data       BLOB    NOT NULL,
    at         INTEGER NOT NULL
);

-- 回放保留策略（单行表，id 恒为 1）
CREATE TABLE IF NOT EXISTS replay_settings (
    id         INTEGER PRIMARY KEY CHECK (id = 1),
    mode       TEXT    NOT NULL DEFAULT 'count', -- count | days
    max_count  INTEGER NOT NULL DEFAULT 200,
    max_days   INTEGER NOT NULL DEFAULT 7,
    updated_at INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX IF NOT EXISTS idx_ctx_segments_ctx ON context_segments(context_id, seq);
```

**写入**：helper 在下行（bot→helper）读循环里按 `CtxID` 累积段输出（单协程，无需锁），收到 `TypeCtxSegEnd` 时把该段 `data` 连同 cwd、seq 落库（`store.AppendSegment`）。保留上下文 `local` 不在 `contexts` 表、会触发外键，故只走内存不回放落库。

**读取与播种**：`handleTerm` 在 `EnsureCtx` 之后调用 `store.RecentSegments(ctxID, core.OutHistoryLimit)` 取出最近 64KB 段，交给 `BOT.SeedCtxReplay` 播种进内存回放缓冲（每条上下文只播一次，bot 下线销毁后自动重新播种）。

**保留策略（二选一，管理员设置）**：`store.ReplaySettings()` / `SaveReplaySettings()`，模式 `count` 或 `days`。保存后立即 `enforceReplayAll` 全表按新策略裁剪；每次 `AppendSegment` 后再对该上下文增量裁剪。**删除不可恢复**，因此存储不会无限增长。单段落库上限 `SegmentLimit = 128KB`（超长只留末尾）。管理员在左侧导航栏「命令历史回放」面板（`panel-replay.js`）设置，接口 `GET/POST /api/replay/settings`（见 `webui/replay_api.go`）。

### 5. 新增 store 方法（新文件 `helper/internal/store/context.go` 与 `replay.go`）

`CreateOrGetContext` / `ListContextsForBot` / `GetContext` / `ListMyContexts` / `CreateRequest` / `ListPendingRequests` / `AnswerRequest` / `GrantAccess` / `ListGrants` / `RevokeGrant` / `UpdateCwd` / `AccessModeFor(ctxID, userID, role)`。

`AccessModeFor` 是核心判定函数：返回 `owner | operate | watch | none`，供 webui 在订阅与输入时调用。

回放相关（`replay.go`）：`ReplaySettings` / `SaveReplaySettings` / `AppendSegment` / `RecentSegments` / `LastSeq` / `ReplayStats`。

## 九、关键取舍与风险

1. **哨兵是最脆弱的一环**。cmd 的 `PROMPT` 注入与 bash 的 `PS1` 继承都需要先做最小验证；用户自定义 prompt、`prompt` 命令、`exec` 之类会干扰。缓解：静默兜底 + 周期重注入。**这是整个方案里最需要实测的部分。**
2. **内存**：每个 ConPTY 实例约占 20–30MB，`maxContextsPerBot = 5` 是硬上限，防止被控端被拖垮。
3. **断线后 shell 保活**有进程泄漏风险，用 `sessionIdleTTL = 10min` 的 GC 兜底。
4. **恢复的边界**：能恢复 cwd、段回放（终端画面）与提示符状态，但**无法恢复进程内状态**（在跑的进程、shell 命令历史文件）。这一点已在需求确认时约定。
5. **本机 DOS 面板**（`helper/internal/panel/bot.go`）没有账号体系，给它一条保留上下文 `ctxID = "local"`（owner 视为本机），保持可用。
6. **授权数据一致性**：`context_grants` 与 core 内存态需要在授权/撤销时同步更新；撤销要立刻断开对应订阅者。

## 十一、验证方式

### 静态与构建

```powershell
# 两端分别执行
gofmt -l .            # 应无输出
go vet ./...
go test ./...

# 跨平台构建（scripts/ 下现有构建脚本）
# Windows: helper.exe / user.exe
# Linux:   helper_linux_amd64 / user_linux_amd64
```

### 端到端（两个普通用户 A / B + 一个观察者 O + 一台 bot）

1. **隔离**：A、B 同时连同一台 bot，各自执行 `cd` 到不同目录，互不影响；`echo %CD%` 各自正确。
2. **私密**：A 执行 `systeminfo`，B 界面上**完全看不到**。
3. **观看授权**：B 对 A 的上下文发起 `watch` 申请 → A 同意 → **A 的下一条命令跑完后**，B 才看到该段输出；再验证 watcher 接入时会回放最近段。
4. **接续授权**：B 申请 `operate` → A 同意 → B 可输入、A 变只读并收到提示；A 点「收回」→ B 输入被拒，锁回 A。
5. **默认可看**：A 打开用户级开关 → B 无需申请即可只读观看 A 的上下文。
6. **恢复**：A 断线重连 → 上下文仍在、cwd 与终端画面（段回放）恢复；重启 bot / helper 进程后再试一次，确认按 DB 的 cwd 重建且画面自动回放。
7. **回放保留策略**：管理员在「命令历史回放」面板切换按条数 / 按天数并保存 → 服务端立即删除超出部分（刷新统计可见段数下降）；再连终端确认仍在保留范围内的画面正常恢复。
8. **观察者**：O 看不到未开放的上下文；申请被拒后仍只读；无法申请 `operate`。
9. **配额**：第 6 个用户在同一 bot 上开上下文被拒绝并给出提示。
10. **全屏程序兜底**：A 运行 `vim` / `top`，B 靠「静默 800ms 兜底」仍能收到分段输出。
11. **本机 DOS 面板**：`bot <ID>` 仍可用（走保留上下文 `local`）。

### 判定口径

以**被控端录像**（`logs/botlogs/<botID>.log`）里的原始字节为准，确认哨兵被正确剥离、段边界与 `TypeCtxSegEnd` 一一对应；不要只看浏览器 DOM 的行数。
