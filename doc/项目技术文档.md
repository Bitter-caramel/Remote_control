## 1. 总体架构：双 Go module 独立编译

**为什么**：操控端（helper）与被控端（user）是两个独立部署、独立升级的程序，
各跑在完全不同的机器上。合在一个 module 里会让「被控端程序把协助端代码一起带上」，
体积、攻击面、耦合都不可控。

**方案**：仓库根目录下两个独立 module：

| 端 | module 名 | 入口 | 运行位置 |
|----|-----------|------|----------|
| 操控端 | `remoteassist-helper` | `helper/cmd/helper` | 协助者机器 |
| 被控端 | `remoteassist-user` | `user/cmd/user` | 被协助机器 |

**实现细节**：
- 每个 module 独立的 `go.mod`，互不依赖；
- 唯一需要「共享」的是通信协议 `protocol/message.go`——因独立 module 无法直接共用包，
  两端各保留**一份内容一致的拷贝**。约定：**修改协议必须同步改两处**，否则握手失败
  （helper 与 user 的 e2e 测试专门覆盖这一层）。
- 编译产物统一输出到仓库根 `bin/`（见 §9.2）。

## 2. 通信层

### 2.1 反向连接模型

**问题**：被控端通常没有公网 IP、不能开放入站端口，操控端无法主动连它。

**方案**：连接方向反过来——**被控端主动外连操控端**（`user.exe → helper.exe:8080`）。

**实现细节**：被控端只需要知道操控端的「地址 + 端口」即可发起 TCP/WebSocket 连接；
操控端监听一个固定端口（默认 8080）。被控端断线后每 5 秒自动重连，无需人工干预。

### 2.2 WebSocket 长连接 + 心跳缓冲

**为什么选 WebSocket**：需要双向、实时、低延迟的字节流（终端是交互式的，不能像
HTTP 请求/响应那样一问一答）；HTTP 升级成 WS 后天然穿透大部分防火墙与代理，且
浏览器端原生支持（Web 控制台复用同一条链路）。

**心跳与缓冲（为什么丢 3 个周期才判下线）**：
- 网络抖动是常态，一次心跳丢失不代表机器没了；
- 被控端每 5s 发一次 `heartbeat`（**只探活、不写日志**，避免日志爆炸）；
- 操控端每 10s 扫描：第 1 次丢失把 BOT 移入「缓存区」继续等；**连续 3 个周期
  （约 30s）未恢复才销毁协程、标记下线**。期间输出先缓存，恢复后补发。
- 被控端正常退出会主动发 `bye`，操控端立即下线，不必等超时。

### 2.3 JSON 消息 + Base64 字节流

**问题**：终端是**原始字节流**——含 ANSI 控制序列，且 UTF-8 多字节字符可能在任意
字节处被分包。直接塞进 JSON 会破坏二进制安全。

**方案**：统一 JSON 消息结构 `protocol.Message`，其中 `data` 字段一律用
**Base64** 承载原始字节。消息类型用字符串常量（`register` / `input` / `output` /
`resize` / `heartbeat` / `bye` / `exec` / `file_put` …）。

**实现细节**：
- 分片不破坏 UTF-8 多字节字符？——不需要关心。Base64 编解码是对「原始字节」的
  无损往返，被控端把 shell 输出的字节流原样编码，操控端原样解码写进终端，
  ANSI 序列与多字节字符都完整。
- 浏览器控制台的终端 WS（`/api/term?bot=<ID>`）走**页面内精简协议**（`{type,data,cols,rows}`），
  它桥接的是操控端**内部** BOT，与远端协议无关，因此不需要两端同步修改。

### 2.4 本地 IPC 安全设计

**场景**：操控端为每台机器弹出「独立终端窗口」，这些窗口进程（`helper.exe -attach`）
需要与本机主进程通信；同时 `helper.exe -cli` 给 AI Agent 提供脚本化调用。

**为什么严格限制**：本机 IPC 是绕过远程鉴权的「近道」，一旦被本机其它进程滥用，
等于本机任何程序都能控制所有被控端。

**方案**（三层防护）：
1. **只监听 `127.0.0.1`**：外部网络不可达；
2. **端口随机**（`127.0.0.1:0`）：不固定端口，降低被扫描命中的概率；
3. **随机令牌**：每次启动重新生成 16 字节令牌，接入必须携带；`agent_endpoint.json`
   落盘（权限 0600）供 CLI 自动发现，退出时删除。

**实现细节**：WS 升级时校验 `Origin`——非浏览器客户端放行，浏览器场景只放行回环来源；
接入后第一条消息必须是令牌握手（5 秒超时）。

## 3. 终端链路

### 3.1 ConPTY / ptmx 真伪终端

**问题**：最早的管道实现（`cmd.exe` 的 stdin/stdout 管道）没有行规程——回显、Ctrl+C
信号、方向键、Tab 补全、全屏程序（vim/top/diskpart）全部不可用。

**方案**：两端都用**真伪终端**：
- Windows：**ConPTY**（Win10 1809+），启动 `cmd.exe /K chcp 65001>nul`；
- Linux：**/dev/ptmx**（PTY），优先 `$SHELL`，回退 bash/sh；
- 老系统 / 其它平台：降级为管道 shell（功能弱，但可编译自测）。

**实现细节**：
- shell **惰性启动**（首次收到输入才创建）、**退出后自动重启**（远端敲 `exit` 不杀会话）；
- 初始尺寸 120×30，接入终端窗口后由实际窗口尺寸覆盖（见 §3.3 中「尺寸同步」）。
- 平台差异用 `_windows.go` / `_other.go` 后缀 + `//go:build` 约束隔离。

### 3.2 编码处理：GBK → UTF-8

**问题**：中文 Windows 的 cmd.exe 默认代码页 936（GBK），其输出直接塞进 JSON 是乱码。

**方案**：
1. 控制台切到 65001 代码页（`chcp 65001`），ConPTY 启动命令同样执行；
2. 输出侧做防御性转换：**合法 UTF-8 原样使用；GBK 编码（936 代码页系统上）转成
   UTF-8 再回传**，保证操控端与浏览器永远拿到 UTF-8。

**教训**：编码问题只靠「假设对方是 UTF-8」不够，必须在边界显式处理。

### 3.3 提示符哨兵与段切分

**问题**：终端是**连续字节流**，裸 PTY 没有「这条命令跑完了」事件。但
「一条命令跑完 = 一次操作」是**观看者同步**与**命令历史回放**的最小粒度，必须造出信号。

**方案：提示符哨兵（sentinel）**。shell 启动时通过**环境变量**注入提示符：
- Windows：`PROMPT` = `$P$G` + `$E]1337;RA;<nonce>:$P$E\`；
- Unix：`PS1` = `\w \$ \[` + `\e]1337;RA;<nonce>:\w\e\\` + `\]`。

其中 `ESC]1337;RA;<nonce>:<cwd>ESC\` 是**不可见 OSC 序列**（终端不渲染 OSC），
nonce 每上下文随机，避免误判用户自己打印的 OSC。

**实现细节**（`user/internal/term/sentinel.go`）：
- 每次 shell 打印提示符，输出流自动带上哨兵；被控端 `sentinelParser` 流式解析：
  - 剥离本上下文的 OSC（其余 OSC 原样透传，不吞用户程序的序列）；
  - 产出两种保序事件：`data`（可显示字节）+ `hit`（段边界，携带 cwd）；
- 边界用「非本 nonce 的 OSC 一律放行」+「未决字节上限 8192」（防止半截 OSC 无限缓存）。

**为什么不能用「固定超时」切段**：输出快慢差异极大——`ls` 毫秒级结束，
`top`/`vim`/装环境可能数分钟无输出。超时切段要么切碎、要么等不到边界；
哨兵给出的是**提示符再次出现 = shell 空闲 = 段结束**的精确信号。

**历史教训：重注入为什么被删**。哨兵是启动时一次性注入的，用户一旦改了提示符
（`prompt` 命令 / 改 PS1 的脚本）哨兵就失效。旧方案检测到失效后往**运行中的 shell
写一条 `set PROMPT=...`**（重注入）把它设回去——但这是「往 shell 里敲命令」：
行规程会**回显**（用户看到乱码）、cmd 语法在 PowerShell 里**直接报错**、
还会和用户正在输入的内容**拼成一行**（回车即报错）。已彻底删除，改用
**静默兜底**：输出静默 800ms 即封一段（`segSilenceFallback`），精度稍低但不打扰用户。
实现上还有一个配套细节：**被控端段序号跨重启续接**（服务端落库最大序号，
重连时下发 `baseSeq`），保证回放顺序单调。

### 3.4 命令历史回放

**问题**：helper 重启 / bot 重启后，内存回放缓冲（最近 64KB）丢失，用户重连
看到一片空白，不知道上次操作到哪。

**方案**：每条上下文在**段结束时**把该段的原始输出落库（`context_segments` 表），
重连时按 `seq` 顺序取出喂给终端，让用户看到上次的画面。内存回放仍是实时首选，
该表只是「冷启动底片」。

**实现细节**（`helper/internal/store/replay.go`）：
- 保留策略由管理员在「命令历史回放」面板设定：**按条数**（默认 200 段）或
  **按天数**（默认 7 天）二选一；策略一改立即清理多余数据，表不无限增长；
- 单段落库上限 128KB（`SegmentLimit`）：超长输出只留末尾，避免 `dir /s` 撑爆库；
- 已知取舍：`local` 保留上下文重启后仅内存回放（不落库）。

## 4. 并发与控制模型

### 4.1 多操作上下文

**问题（旧模型）**：一台机器一个 shell、所有人共用——一个人操作时其他人只能干看，
操作互相干扰，无法区分「谁做了什么」。

**方案（新模型）**：**每用户每 bot 一条独立操作上下文**。数据库建立树形结构
「用户ID → botID → 操作上下文」，每条上下文在被控端对应一个独立 shell 进程
（各自 cwd / 环境 / 前台程序互不影响）。非观察者用户可同时操控 bot，各自查看
自己的上下文。

**实现细节**：
- `CtxID = c_<botID>_<ownerID>`：确定性 ID 而非自增，`CreateOrGetContext` 天然幂等，
  DB / 内存态 / 协议三处永远一致；
- 访问模式四级：`owner > operate > watch > none`；
- 观看 / 接续他人上下文需**发起申请并获 owner 同意**（`context_grants` / `context_requests`）；
- 支持 A、B 同时观看同一上下文，但保留**占用状态防争抢**；
- 被控端单机上下文上限 5（每个 ConPTY 约 20-30MB，防被控端被拖垮）；
- 空闲会话超过 `sessionIdleTTL`（10 分钟）自动回收，防 shell 进程泄漏。

### 4.2 订阅者广播 + 独占输入

**问题**：同一台机器可被多个接入者（多个 DOS 窗口、多个浏览器页面）同时打开，
画面要共享，但输入必须唯一。

**方案**：
- **输出广播**：BOT 把远端输出广播给所有订阅者，并保留最近 64KB 回放缓冲
  （新接入者立刻看到上下文，而不是一片空白）；
- **输入独占**：同一时刻只有一个「占用者」能输入，其余接入者按 FIFO 排队；
  占用者释放（关闭 / 主动放弃 / 闲置超时）后队首自动接棒；
- **接续上下文时输入闸门**：被授权 operate 的观看者，其订阅角色要同步升降
  （`context.go`），输入闸门按实时锁判定（`server.go`），避免「授权后输入被静默丢弃」。

### 4.3 闲置下线确认

**问题**：占用者长时间挂机，机器控制权被白白占着，别人进不来。

**方案**：占用者连续 5 分钟**既无输入也无输出**时，推送 `idle_prompt` 并倒计时
1 分钟：点「是」或超时→收回控制权让位；点「否」→重新计 5 分钟。

**实现细节**：判定「有操作」**包含机器有输出**——装环境 / 拉依赖这类持续刷屏的
任务不会被误判打断（这是对比上一版「只看输入」的关键修正）。

## 5. 插件化架构

### 5.1 前端注册表

**为什么**：控制台是「外壳 + 可插拔面板」。外壳不应知道每个面板长什么样，
否则每加一个功能都要改外壳，违背开闭原则。

**方案**（参考 DSH Cordis 理念）：
- `registerPanel({id,name,version,layer,depends})` 注册左侧导航面板；
- `UI.dock.register({id,name,order,minRole,mount})` 注册底部 Dock 面板；
- `UI.console.registerTool({id,name,order,applies,mount})` 注册控制台工具
  （工具需实现 `applies(os)` 按机器类型过滤）；
- 外壳只读注册表并按拓扑排序渲染。

### 5.2 后端 feat 注册表

**为什么**：后端 Web 控制台（`webui/server.go`）早期的路由是集中式 `Register` 方法，
加一个功能就要改它。改为与前端对称的插件式：

- `feat` 子包：`Deps`（依赖集合 M/Prog/St/Auth）、`Manifest`（ID/Name/Layer/Order/Mount）、
  `RegisterFeature`、`MountAll`；
- `features/` 子包：每个功能一个包，`init()` 里自注册；
- `webui/features.go`：集中空白导入清单（`_ ".../features/file"`）触发 init。

**为什么注册表必须是独立 `feat` 子包**：功能子包在 `init()` 里调用
`feat.RegisterFeature`，而 `webui` 要空白导入功能子包触发 init——若注册表定义在
`webui` 包内，会形成 `webui → features/x → webui` 的**导入环**。
`feat` 谁都不依赖，两边都引它，天然无环。

### 5.3 L0-L3 分层

项目按 **L0 内核 → L1 基础功能 → L2 具体功能 → L3 用户扩展** 分层，每层模块
实现类似 DeepSeekHarness「everything is a plugin」的机制，支持替换与扩展。
前端 Manifest 含 `layer` 字段即为此设计；后端功能同样在 Manifest 里标注 `Layer`。

## 6. 安全与鉴权

### 6.1 PBKDF2 口令存储

**为什么**：口令绝不能明文或简单哈希存储；每账号要独立盐，防彩虹表。

**方案**（`helper/internal/auth`）：
- 口令以 **PBKDF2-HMAC-SHA256** + **每账号独立随机盐**哈希入库（`users` 表存
  salt / hash / iterations）；
- **账号不存在与口令错误共用同一错误**，且对不存在的账号做一次等价耗时的派生
  （dummy salt），防止通过响应时间枚举账号。

### 6.2 自实现 HS256 JWT 会话

**为什么自实现而不引 JWT 库**：本项目只需要极小子集（HS256 + 几段校验），
自实现可精确控制字段与撤销语义，也避免依赖膨胀。

**方案**：
- 登录后签发 HS256 签名的令牌，`Claims{Sub,UID,Ver,SID,Iat,Exp}`；
- **口令永不写进令牌**，令牌里只有会话 ID 与账号 ID；
- 签名密钥独立存储于 `helper.key`（权限 0600，敏感文件入 .gitignore）；
- 会话登记入库（`sessions` 表），**登出只撤销单个会话**（`RevokeSession(SID)`），
  其它用户 / 其它会话完全不受影响；
- **`Valid` 每 5 秒复查**长连接（终端 WS 握手后鉴权不会自动重放），
  管理员踢下线、停用账号、改权限立刻作用到已打开的页面；
- Cookie：`httpOnly` + `SameSite=Strict`；未启用 TLS 时 `Secure=false`。

**历史教训**：早期方案「服务器临时管理盐值、下线即丢弃」会导致**所有用户令牌同时失效**；
现实现改为「每账号独立随机盐常驻入库 + 签名密钥独立存储 + 登出仅撤销单个会话」。

### 6.3 三级角色 + 机器可见等级

**方案**：角色三档——观察者（仅查看）/ 普通用户（可执行操作）/ 管理员（全部权限）；
每台机器带 `min_role` 可见等级，角色值 ≥ 等级才可见可操作。
管理员专属：用户管理（增删改权限）、Bot 管理（设置可见与操作权限等级）。
角色值每次请求都从数据库现取，因此**降权即刻生效**，无需重新登录。

### 6.4 SQLite：纯 Go、无 cgo

**为什么选 SQLite + modernc.org 驱动**：单机应用需要持久化（账号 / 机器 / 会话 /
审计 / 段回放），SQLite 零运维；`modernc.org/sqlite` 是**纯 Go 实现，不依赖 cgo**，
因此 `CGO_ENABLED=0` 的 Linux 交叉编译依然可用（这是选它而非 mattn 驱动的原因）。

## 7. 文件传输

### 7.1 分片协议

**问题**：终端通道的 `data` 是 Base64 文本，不适合大文件直接传输；且没有流控
会让内存 / 带宽失控。

**方案**：**32KB 分片、逐片同步**：
- 投放（helper→user）：`file_put` 逐片下发（首片带 Path/ChunkSize，末片 `ChunkLast`），
  被控端每片回 `file_put_ack`（末片 ack 带回最终写入路径）；
- 下载（user→helper）：helper 逐片发 `file_get`，被控端回 `file_get_chunk`。

**实现细节**：
- 逐片同步天然限速（发一片、等一片 ack），无需额外令牌桶；
- 默认落点：被控端工作目录下的 `received/` 文件夹；
- 不设大小硬上限（按机器磁盘与网络自平衡）。

### 7.2 待回包注册表

**与 exec 的区别**：exec 是一次性 Resolve 后删除；文件传输一个 FileID 对应多片，
发起方用同一个 channel **逐片等待**，全部完成或超时后由发起方注销。

**实现细节**（`helper/internal/core/filexfer.go`）：
- `RegisterFile(fileID, botID)` 登记等待通道（FileID 冲突返回 false）；
- `WaitFileAck` 逐片等待，60s 超时返回 nil；`FetchFileChunk` 发请求+等回片（下载侧）；
- `ResolveFile` **非阻塞投递**：发起方放弃后 channel 残留，不能让 uplink 读协程卡住；
- bot 下线时 `failFilesOfBot` 统一投递 nil 唤醒所有未完成会话；
- Web 控制台与 CLI 面板（`put`/`get` 命令）共用同一份 `WaitFileAck/FetchFileChunk`。

## 8. 前端工程

### 8.1 go:embed 内嵌、离线可用

**为什么**：控制台是一个单 exe 分发，若依赖外网 CDN 加载 xterm.js，内网环境
直接白屏。

**方案**：全部前端（index.html / css / js / vendor 里的 xterm.js 5.5 + fit 插件）
通过 `go:embed` 打进 `helper.exe`，**不依赖外网**。代价：**改前端文件必须重新编译**，
不存在「改完刷新即生效」。

### 8.2 SPA hash 路由

**方案**：`location.hash` 实现单页应用切换（`#term`、`#users` 等），切换不刷新页面，
规避了对服务器路由配置的依赖；每个面板自注册后由外壳渲染。

### 8.3 底部 Dock 与工具状态缓存

**方案**：底部面板仿 VSCode panel（默认收起），用 `UI.dock.register` 注册扩展；
控制台是前端视图，随当前上下文/机器切换而重挂。

**坑**：Dock 收起时 `unmount` 会清空 DOM，导致已填写的表单状态丢失
（例如已选择的待投放文件）。修复：工具级模块缓存（`tool-file.js` 的 `cached`
对象：文件句柄 / 目标路径 / 下载路径），收起展开后恢复，而不是改 Dock 生命周期。

## 9. 平台适配与构建

### 9.1 交叉编译与 CGO_ENABLED=0

**方案**：Windows 上直接编译 Linux amd64 版本：
`GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build`。得益于 §6.4 的纯 Go SQLite 驱动
与「无 cgo」原则，产物为纯静态二进制，CentOS 等老系统直接可跑。

### 9.2 构建脚本与 bin/ 约定

- 所有产物统一输出到仓库根 `bin/`（不入库，已 gitignore）；
- 构建脚本集中在 `scripts/`（helper/user × windows/linux/dll 六种）；
- 被控端 Linux 无界面场景提供 `start / stop / status` 后台子命令（daemon + pid 文件）。
